## Reproduction before fixes

The first focused storage run failed all 11 audit cases, the zero-weight test failed, and the deadline/cancellation tests failed three cases against the original download function. The original production build reproduced the corrupt-only clear lockout, both wrong-side previews, stale footer, missing repetition history, failed-batch recovery and two-tab attempt loss.

The initial cancellation test was too weak: duplicate IDs hid repeated engine work, and cancellation could occur before the interrupted search began. It was strengthened to wait for a game-two position command and count distinct engine starts. A separate archive of the audited source reproduced three game-two starts instead of the expected two. This archive used the patched build dependency; it established the original application behavior, not an original-dependency release hash.

Static reproduction also confirmed whole-record writes, the stale batch tail and full-library serialization on every App render. Regression work caught and fixed a player-save timing race where an immediately typed practice answer could be cleared by the eventual player update.

## Verification

All 15 findings are fixed locally. `npm run check` passed formatting, types, 84 unit tests (47 web + 37 contracts) and the production build. `npm audit` reports zero vulnerabilities; `git diff --check` passed.

The comprehensive browser run completed 119/120 checks: Chromium 40/40, Firefox 40/40 and WebKit 39/40. One existing WebKit cancellation test timed out while Playwright waited for a moving Cancel button to become stable; the analysis completed before it clicked. The test now holds the first requested search open before clicking Cancel, and the targeted follow-up passed on all three browsers (3/3). No application change was needed for this test adjustment. All 120 configured checks have passing evidence across the comprehensive run and this follow-up; this is not a claim that the initial run was entirely green.

The audit's earlier WebKit browser-launch failures did not reproduce: WebKit launched and exercised the application locally. No environment installation or configuration change was made during this task, so the previous launch failure's root cause remains unestablished.

## Limits

Backups have no arbitrary library-wide limit, but still need sufficient browser memory and storage. A failed save leaves completed results in session memory; download recovery data before closing or refreshing. Batch resume is for the current session, while completed saved games survive refresh. Very large libraries beyond the tested fixture are not a universal responsiveness guarantee.

All browser results are local production-build automation on Windows. Phone-sized viewport tests are not physical-device tests. WebKit automation is not verification on actual Safari/iOS. No hosted-site or physical-device verification, deployment or publication was performed.
